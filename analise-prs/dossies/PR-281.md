## Bugs Fixados (4)

### 1. RegExp g-flag lastIndex

**Problema:** expressões regulares criadas com a flag `g` (global) e reutilizadas entre múltiplas chamadas acumulam o valor de `lastIndex`. Quando o mesmo objeto RegExp era usado para testar várias strings, após um match bem-sucedido o `lastIndex` ficava apontando para a posição após o match anterior, causando falsos negativos nas chamadas seguintes.

**Sintoma:** o script de auditoria falhava em detectar padrões em SQLs que deveriam ser detectados, dependendo da ordem de execução.

**Fix:** objetos RegExp com flag `g` são agora resetados (`regex.lastIndex = 0`) antes de cada uso, ou recriados por chamada quando a reutilização não é necessária.

---

### 2. CREATE_TABLE before stripComments

**Problema:** o parser de SQL verificava a presença de `CREATE TABLE` antes de remover comentários SQL (`-- ...` e `/* ... */`). SQLs com comentários extensos antes da declaração de `CREATE TABLE` não eram detectados corretamente.

**Sintoma:** migrations com cabeçalho de comentário descritivo (padrão do projeto) não eram classificadas como `CREATE TABLE` pelo script de auditoria.

**Fix:** a função `stripComments` agora é chamada **antes** da detecção de `CREATE TABLE`, garantindo que comentários não interfiram na classificação.

---

### 3. SQL Injection em Probe Literals (pgLit)

**Problema:** literais de string inseridos diretamente em queries de probe sem escape. Se o nome de uma tabela ou coluna contivesse caracteres especiais (aspas, cifrão, etc.), a query resultante poderia ser mal-formada ou explorada.

**Sintoma:** probes falhavam com erro de sintaxe SQL quando o nome do objeto continha caracteres especiais. Em cenário adversarial, poderia ser explorado via nomes de objetos maliciosos no schema.

**Fix:** todos os literais inseridos em queries de probe passam agora pela função `pgLit` (escape de literal Postgres), garantindo que valores sejam corretamente escapados com aspas simples e escape de aspas internas.

---

### 4. Views vs BASE TABLE

**Problema:** o filtro `table_type = 'BASE TABLE'` em `information_schema.tables` excluía views de algumas verificações de auditoria onde views deveriam ser incluídas. O script tratava toda consulta a `information_schema.tables` com esse filtro, mesmo em contextos onde views são objetos legítimos a auditar.

**Sintoma:** views existentes no schema não apareciam nos relatórios de auditoria que deveriam incluí-las.

**Fix:** o filtro `table_type = 'BASE TABLE'` é aplicado apenas onde explicitamente necessário (verificações de tabelas físicas). Verificações que devem incluir views usam filtro adequado (`table_type IN ('BASE TABLE', 'VIEW')`) ou sem filtro de tipo.
